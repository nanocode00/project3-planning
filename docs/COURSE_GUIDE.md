# 평가조건을 충족하는 방법 — 수업자료 적용 가이드

최초 정리: 2026-10-26. **2026-10-28 추가된 3주차01~19강을 반영했습니다.** 강의별 적용 기준과 한계는 [수업자료 목록](COURSE_SOURCES.md)의 W항목에서, 구현 방법은 이 문서의 각 H절에서 확인하세요. **공식 수량·감점은 [GATES](GATES.md)와 [EVALUATION](EVALUATION.md)**을 따릅니다. 이 문서의 구현 순서·파일 이름·시험 사례는 그 기준을 달성하기 위한 **팀 제안**입니다. 특정 라이브러리·모델 선택을 새 필수 조건으로 추가하지 않습니다.

각 절은 **수업에서 가져올 것 → 프로젝트에 적용할 것 → 남길 증거 → 추가 구현** 순서입니다. R/L/D 등 출처 ID는 [수업자료 목록](COURSE_SOURCES.md)의 원본 파일·셀로 연결됩니다. 체크 ID별 역방향 연결은 [조건별 대응표](COURSE_COVERAGE.md)에 있습니다.

이번 작업은 원문 소스·일부 PDF 페이지·스크립트의 **정적 조사**입니다. 실행·학습·API·DB·배포 검증은 하지 않았고, 완료 체크도 바꾸지 않았습니다. Deep Agents·무인 에이전트·실제 외부 전송을 새 필수 요건으로 추가하지 않습니다. 필수·가산 기준은 프로젝트 가이드를 따릅니다.

## H01

**문제·시장 근거, 페르소나, 대체재 비교 — E1, 주제서**

수업 근거: [PM](COURSE_SOURCES.md#pm) p.78~87(문제·페르소나·MVP·사용자 흐름), p.119(공고 문장 분해), p.127~131(개인 기여·의사결정·실험 증거).

1. 목표 직무의 채용 공고 **50건**을 `URL·회사·직무·확인일·업무·필수/우대 역량` 표로 수집하고 중복을 구분합니다. 문장을 역량 키워드로 나눠 빈도와 프로젝트가 증명할 역량을 연결합니다. 수업의 “공고5~10개” 예시는 분석 방법만 참고하고 **3차의50건**을 적용합니다.
2. 한 사용자의 반복 문서 업무를 정하고, 현재 해결법·소요·불편·AI가 필요한 이유를 씁니다. 가상의 사용자와 검증한 사실을 분리합니다. 지불 주체·수요가 아직 가설이면 그 상태를 적습니다.
3. 페르소나의 목표/현재 방법/불편/기대와 사용자 행동 흐름을 작성합니다. **고객 여정 맵**에는 단계별 행동·접점·pain point·개선 기회를 추가합니다. 교안의 User Flow 그림만으로 여정 맵을 다 했다고 보지 않습니다.
4. 동일 질문 **5개**를 범용 챗봇과 프로젝트에 넣고 답변·근거 링크·오답/거절·업무 활용성·한계를 나란히 기록합니다. 질문·모델·시각·조건도 남깁니다. 외부 검토 **1명**의 의견과 반영/미반영 이유를 연결합니다.

증거: 공고50건 목록·키워드 집계, TOPIC, 페르소나/여정 맵, 질문5개 비교 원문, 외부 검토 기록. **추가 작업:** 우리 산업 조사·지불 주체 검증·외부 검토는 강의 예시로 대체할 수 없습니다.

## H02

**코퍼스50문서·고유1만청크·manifest — G3-1/2/4**

수업 근거: [R07](COURSE_SOURCES.md#r07) 셀13/17/21/22/26(목록→원문→정제→저장), [R11](COURSE_SOURCES.md#r11) 셀20/22/32(manifest·호환성 검사), [D07](COURSE_SOURCES.md#d07) 셀10/17/21(원문 해시·기록 재로드), [D08](COURSE_SOURCES.md#d08) 셀16(원문/청크/벡터 인수인계 검증).

1. 문서 식별자·원문 URL·수집일·파일 SHA-256·정답 기준일을 보관합니다. DART라면 목록의 접수번호를 받아 ZIP/XML/HTML 원문을 텍스트화하는 R07 흐름을 사용합니다. 다른 산업이면 수집기만 바꿉니다.
2. 청크에는 `chunk_id, source_id, text, text_sha256, page/pages, parser/version`을 둡니다. **원문 파일 해시와 청크 본문 해시는 별개**입니다. 파일50개만 세거나 청크 ID 개수만 세지 않고, manifest에서 고유 문서와 **본문 해시 고유값**을 다시 집계합니다. 복제·약간의 변형으로 수를 늘리지 않습니다.
3. 원문 길이·보존 길이·잘림 여부·문서당 청크 수를 기록합니다. DART 앞1500자 예시처럼 본문을 자른 인덱스라면 누락 범위를 드러내고 뒤쪽 정답도 확보합니다. 채용 공고는 코퍼스 집계에서 제외합니다.
4. 인덱스 manifest에 코퍼스 버전·본문/ID 순서 지문·청킹 설정·임베딩 모델·차원·정규화·파서 버전을 기록합니다. 저장 후 재로드하고, 질의 모델/차원/코퍼스가 다르면 검색 전 실패하게 합니다.

증거: manifest·고유 문서≥50/본문해시≥10,000 집계 로그·집계 명령·호환성 실패 사례·원문 접근/재배포 조건. **추가 작업:** 수업 샘플의 규모가 현재 주제 요건을 충족한다고 가정하지 말고 팀 데이터로 다시 셉니다.

## H03

**문서 파싱≥1종·원문 대조≥3건 — G3-3, E2-1**

수업 근거: [D01](COURSE_SOURCES.md#d01) 셀12~13(세로 사이드바 오염), [D02](COURSE_SOURCES.md#d02) 셀9/18(대표1쪽 Docling·시간 추정), [D03](COURSE_SOURCES.md#d03)(표 검산·차트 보존), [D05](COURSE_SOURCES.md#d05) 셀15/18(쪽 출처·역검증), [D06](COURSE_SOURCES.md#d06)(조/억/만·조사·NFC), [D11](COURSE_SOURCES.md#d11)·[D12](COURSE_SOURCES.md#d12)(선택 OCR/VLM).

1. 실제 코퍼스에서 본문·표/복잡한 배치·텍스트 누락 같은 대표 사례 **3건 이상**을 고릅니다. 원문 화면/쪽 번호와 추출문을 나란히 저장하고 읽기 순서·빠진 문장·수치/단위·표 위계를 사람이 확인합니다.
2. 텍스트 PDF는 먼저 pypdf를 보고, 배치가 깨지면 Docling 대표1쪽을 비교합니다. 스캔은 텍스트 레이어 진단 후 필요한 쪽만 OCR, 차트/복잡표는 VLM 추출값을 원문과 대조하고 의심값을 검토 대기로 둡니다. 모든 파서를 쓰는 것은 필수가 아닙니다.
3. 청크가 여러 쪽에 걸치면 페이지 목록을 유지합니다. 페이지 번호가 맞아도 추출 내용이 맞다는 보장은 없으므로 숫자/단위 대조를 별도로 합니다.

증거: `원문ID/쪽·원문 이미지·추출문·오류·선택 파서/버전·처리시간·판정자` 대조표≥3행. **추가 작업:** 강의의 오류 스크린샷 대신 우리 코퍼스의 대조를 남깁니다. OCR/VLM은 필요할 때만 선택하며 API 전송·실제 실행을 이 문서 작업에서는 하지 않았습니다.

## H04

**청킹·임베딩 선택과 처리량 — E2-2, E4-7**

수업 근거: [R08](COURSE_SOURCES.md#r08)(fixed/recursive·overlap), [R18](COURSE_SOURCES.md#r18)(임베딩/임계값 이식), [R19](COURSE_SOURCES.md#r19) 셀28/31(문항별 A/B), [D04](COURSE_SOURCES.md#d04)(재귀/시맨틱/late), [D08](COURSE_SOURCES.md#d08) 셀24/26/34/40(배치·재시도·평가·차이 구간).

청킹 크기/overlap 또는 분할 방식 중 **한 요인**을 고정 코퍼스에서 비교합니다. 임베딩 비교에서는 같은 본문·질문·정답과 모델별 올바른 질의/문서 설정을 사용합니다. 문서 벡터와 질의 벡터는 같은 모델 공간이어야 하며, 모델을 바꾸면 거절 임계값도 개발 표본에서 재검토합니다.

공식은 “둘 이상 비교한 선택 근거”를 요구합니다. 팀 실행안은 청킹2대안·임베딩2대안을 각각 통제 비교하되 전 조합을 무조건 돌리지 않는 것입니다. **100건 로컬/API 처리량**에서 입력 건수·문자/토큰·초·비용·장비·cold/warm·모델 캐시를 기록하고, 1만청크 처리 일정은 길이 차이를 고려해 추정으로 표시합니다. 로컬 모델을 선택하면 미리 받아 `HF_HUB_OFFLINE=1`에서 필요한 경로를 확인합니다.

증거: 대안별 검색지표·저장량·처리시간/비용·변경 문항·채택 이유. **추가 작업:** 현재 D08 기본은 `REBUILD_PDFS=False`로 저장 청크/벡터를 검증해 재사용합니다. 이 실행 시간을 PDF 파싱/임베딩 실측으로 쓰면 안 됩니다. README의 과거 설명보다 현재 셀16/18을 확인합니다. 강의 모델의 과거 성적은 우리 모델 선택 근거를 대신하지 않습니다.

## H05

**하이브리드·리랭킹·필터·실패 분석 — E2-3/5/6**

수업 근거: [R06](COURSE_SOURCES.md#r06) 셀11/14/18(BM25·벡터·RRF), [R12](COURSE_SOURCES.md#r12) 셀19/36(후보 재정렬), [R10](COURSE_SOURCES.md#r10)(선필터/후필터), [D09](COURSE_SOURCES.md#d09) 셀44/51(SQL 필터·출처 결합), [R14](COURSE_SOURCES.md#r14)(검색 실패 분류).

1. 같은 청크 ID 체계에서 BM25와 벡터의 후보 순위를 만들고 RRF로 합칩니다. 서로 다른 척도의 점수를 그대로 더하지 않습니다. 후보수·RRF 설정을 기록합니다.
2. 융합 후보 안에서 리랭킹하고 최종 k개를 고릅니다. 후보에 정답이 없으면 리랭커로 회복할 수 없으므로 **후보 Recall과 최종 순위**를 구분합니다. R12의 본문 예제는 LLM으로 점수를 매겨 cross-encoder 원리를 설명하는 것이며, 특정 로컬 CrossEncoder가 이미 완성됐다는 뜻은 아닙니다.
3. 기관·기간·사용자 권한 필터는 후보 검색 단계에 적용합니다. D09처럼 SQL 조건과 벡터 검색을 결합하고 출처 필드를 함께 돌려줍니다. 후필터가 0~2개만 남겨 우연히 거절을 늘리는지 별도 집계합니다.
4. 실패를 코퍼스에 없음/파싱·청킹 손실/후보 못 찾음/후보에 있으나 순위 낮음/인용·생성 실패로 나누고, 각 원인에 맞는 한 요인만 고쳐 다시 잽니다. BM25 추가, 리랭킹 추가를 각각 분리한 비교 기록을 남깁니다.

증거: 같은 문항의 BM25·벡터·RRF·리랭킹 순위/정답 ID·필터 전후 건수·Recall/MRR·지연·실패 유형표. 하이브리드가 지는 문항도 기록합니다.

**2026-10-28 추가자료 적용:** [W12](COURSE_SOURCES.md#w12)의 search_fn 교체·필터/동점/HNSW 비교를 추가로 참고합니다. DB교체 전후 동일질의의 후보ID/순위·Recall을 비교하며, 기존 rag_core의 회사명/템플릿휴리스틱을 다른 도메인에 그대로 적용하지 않습니다.

## H06

**단일 그래프 → Supervisor+서브2개 이상 — G4-1/5, E3-1/2/3**

수업 근거: [L02](COURSE_SOURCES.md#l02)·[L03](COURSE_SOURCES.md#l03)·[L04](COURSE_SOURCES.md#l04)(State/조건부 엣지/리듀서), [L17](COURSE_SOURCES.md#l17)(문서 채점), [L18](COURSE_SOURCES.md#l18) 셀23/24/28(재검색·종료), [L20](COURSE_SOURCES.md#l20)(단일 RAG 캡스톤), [A23](COURSE_SOURCES.md#a23) 셀20(구조화 Supervisor), [L14](COURSE_SOURCES.md#l14) 셀35/41/44(부모·서브 상태 변환).

2. L18의 조건부 엣지처럼 충분한 근거·시도 상한·정체를 보고 생성/거절/재검색을 결정합니다. 강의의 `최대시도=2`는 예시이며 프로젝트 공식 상한은 아닙니다. 상한과 예산은 사전 합의합니다.
3. D5에는 A23의 `Task.agent: Literal[...]` + `with_structured_output` 라우팅 패턴을 가져와 **Supervisor + 검색 에이전트 + 작성/검증 에이전트** 이상으로 나눕니다. 세 역할을 단순 함수명만 바꾸지 않고 각 입력·출력·도구·책임을 정의합니다.
4. L14 래퍼처럼 서브그래프에 필요한 질문/근거만 넘기고 검증된 반환 필드만 부모에 합칩니다. 전체 메시지를 모두 공유하는 A23의 글쓰기 예제나 전역 `OUTLINE`은 그대로 사용하지 않습니다. 역할별 실제 입력 로그로 컨텍스트 경계를 확인합니다.

## H08

**로그인·사용자 격리·DB 시멘틱 메모리 — G1-2, G4-3/4**

수업 근거: [L06](COURSE_SOURCES.md#l06) 셀20/27/30(사용자/세션 키·누출 시험), [L07](COURSE_SOURCES.md#l07) 셀13/16/19/22/29/32(namespace·Runtime context·기억 갱신/만료/삭제), [S12](COURSE_SOURCES.md#s12)(승인자 권한), [D09](COURSE_SOURCES.md#d09)(DB·벡터·메타데이터 기반 검색의 기초).

1. 로그인 결과로 서버가 확인한 사용자 ID를 얻어 Runtime context에 주입합니다. 요청 본문의 `user_id`만 믿지 않고 thread 읽기/쓰기/재개 때도 소유권을 확인합니다. 해시로 thread ID를 만드는 것은 인증을 대신하지 않습니다.
2. 사용자의 세션별 대화는 thread로, 세션을 넘어 쓸 선호/프로필/확정 사실은 `("users", uid, ...)` 같은 Store namespace로 나눕니다. 검색 근거·이번 답변은 기본적으로 State에 두고 자동으로 장기 기억에 넣지 않습니다.
3. L07의 `put/get/search/delete` 패턴에 기억할 정보·근거·saved_at·수정/삭제·만료 정책을 붙입니다. 잘못 저장된 선호를 수정한 뒤 새 thread에서 수정값이 쓰이는지 확인합니다.
4. 프로젝트에서는 **DB 기반 Store + 임베딩을 이용한 의미 검색**을 추가합니다. 사용자의 기억을 저장→표현이 다른 질의로 해당 사용자 namespace에서 의미 검색→응답 활용→재시작 후 유지→수정/삭제 후 검색 반영까지 시험합니다. 문서 코퍼스 벡터 검색과 사용자 기억 검색을 혼동하지 않습니다.
5. 평가 계정 A/B의 표식·선호를 서로 다르게 넣어 같은 세션명으로 교차 호출합니다. 정상 분리뿐 아니라 A가 B의 thread를 조회/재개하려는 요청도 거부되는지 확인합니다. 두 계정의 실서비스 비밀번호는 DM 제출합니다.

증거: 로그인 시나리오·교차 소유권 거부·대화/기억 격리·의미 검색 결과·수정/삭제·DB 재시작 지속성. **추가 작업:** L07 본문 `InMemoryStore.search(namespace)`는 namespace 내 항목 조회 예제이며 **DB 영속 시멘틱 검색 완성본이 아닙니다**. 로그인·DB Store·의미 인덱스 설정·접근통제까지 구현해야 합니다. D09의 코퍼스 테이블만 연결해도 G4의 Store가 완성되는 것은 아닙니다.

**2026-10-28 추가자료 적용:** [W08](COURSE_SOURCES.md#w08) 셀15/35/47은 검색 후보의 access 선필터·구조적 유출 판정을 지원합니다. [W-APP](COURSE_SOURCES.md#w-app)의 공통API키 인증과 사용자권한 인자만으로 사용자별로그인/thread·Store소유권을 충족했다고 보지 않습니다. 새자료에도 DB시멘틱Store의 완성예제는 없습니다.

**인용 코드 검증·거절·5지표 — G5-7, E3-5**

수업 근거: [R15](COURSE_SOURCES.md#r15) 셀18/21/35(허위 인용ID·문장 인용·숫자 대조), [R16](COURSE_SOURCES.md#r16) 셀23/31/34(검색 게이트·거절 오류 비용), [L20](COURSE_SOURCES.md#l20) 셀35/44(인용 검증·실패 시 거절), [S14](COURSE_SOURCES.md#s14) 셀27(채점기 보정).

증거: 원시 질문·검색 근거·답변·코드 검증·사람 판정·5지표 표. **추가 작업:** 강의의 키워드/정규식 거절 탐지와 ID 검사만으로 의미적 정답 채점을 대체하지 않습니다. 거절 임계값은 개발 표본에서 정하고 동결 평가셋 결과를 보고 유리하게 맞추지 않습니다.

## H12

**핵심 코드 변이 검증≥3건·CI — M, E3-8, E4-5**

수업 근거: [L06](COURSE_SOURCES.md#l06) 셀30(정상 키와 모두default 비교), [L18](COURSE_SOURCES.md#l18) 셀28(상한 없는 갈림길), [L20](COURSE_SOURCES.md#l20) 셀35(인용검증), [MCP-CHECK](COURSE_SOURCES.md#mcp-check)(위반 시 exit1). 공식3건 기준은 PDF p.17.

팀 제안 사례는 **실제 루프 상한을99로 변경해 반복 제한 테스트 실패**, **namespace를 공유값으로 바꿔 A/B 누출 테스트 실패**, **허위 인용 차단을 제거해 존재하지 않는 출처 테스트 실패**입니다. 같은 상수를 읽어 자기 자신과 비교하는 테스트는 사용하지 않습니다. 각각 `원본PASS → 코드1줄 변이 → 의도한 이유로 FAIL → 원복PASS`와 명령·SHA·검토자를 저장합니다. 장애나 API 오류로 난 실패를 변이 검출로 세지 않습니다.

수업 근거: [GRAPH02](COURSE_SOURCES.md#graph02)(집계·다홉·시간 질의), [GRAPH05](COURSE_SOURCES.md#graph05)(벡터 후보+관계 확장), [GRAPH08](COURSE_SOURCES.md#graph08)(구축 비용/시간).

우리 업무에서 벡터 단독이 답하기 어려운 **관계·다홉·집계·최신성** 질문 유형을 먼저 정의합니다. 문서에서 노드/관계를 만들고 원문출처·정확성 확인을 남긴 뒤, 벡터로 찾은 대상을 그래프로 확장하거나 구조 질의로 답합니다. 같은 문항/정답으로 벡터 단독과 그래프 연계 결과를 비교하고 관계누락·집계오류·추출비용을 보고합니다.

증거: 질문유형·그래프 스키마/원문·동일셋 전후·실제 출력·구축/질의 비용. **적용 주의:** 예제 법안300건·관계 조회 성공만으로 G3 규모나 프로젝트 개선을 충족하지 않습니다. 예제의 결과 필드 증가를 정답률 개선으로 바꿔 쓰지 않습니다. 그래프 구축/초기화 스크립트를 이번 조사에서 실행하지 않았습니다.

**2026-10-28 추가자료 적용:** [W18](COURSE_SOURCES.md#w18)의 그래프도구연결/미연결 결과를 추가 참고합니다. 그래프에 연결됐다는 것과 같은평가셋에서 벡터보다 나아졌다는 것은 별도증거입니다. 미연결오류를 반환하고 진행한 실행은 가산점의 실제그래프비교가 아닙니다.

## H20

**MCP와 Skill 통합 +3 — B4**

수업 근거: [A17](COURSE_SOURCES.md#a17)(FastMCP 서버·도구계약), [A18](COURSE_SOURCES.md#a18)(여러서버 client·부분실패), [MCP-README](COURSE_SOURCES.md#mcp-readme) STEP8/10(계약검사·Skill/reference), [SKILL-EX](COURSE_SOURCES.md#skill-ex)(도메인 절차·판정규칙·한계), [MCP-CHECK](COURSE_SOURCES.md#mcp-check)(선언/구현 대조).

3차 검색 기능을 FastMCP 도구로 노출하고 `query/filters/k → 근거ID·본문·출처·한계` 같은 입력/출력 계약을 고정합니다. LangGraph 에이전트가 **MCP 클라이언트로 실제 호출**하는 trace를 남기고 서버오류/부분실패를 처리합니다. 별도로 도메인 판단 순서·인용/승인 규칙·금지 범위를 `SKILL.md`와 참조 기준에 분리해 에이전트 실행에 실제로 주입/사용합니다.

동일 평가셋·모델·검색조건을 고정하고 **Skill 유무만** 바꿔 비교합니다. MCP 서버 존재 또는 파일만 만든 것으로 둘 다 했다고 보지 않습니다. 기존2차 예제를 재사용했다면 3차에서 새로 추가하거나 RAG와 연결한 부분을 명시합니다.

증거: MCP 계약/실제호출·Skill 내용/적용로그·동일셋 유무차이·신규 연계 diff. **추가 작업:** site-analysis는 입지판정 문서 예시이며 우리 도메인 Skill이 아닙니다. 이 조사에서는 해당 파일을 수업자료로 읽었을 뿐, 그 도구나 업무를 실행하지 않았습니다.

**2026-10-28 추가자료 적용:** [W17](COURSE_SOURCES.md#w17)에서 Skill은 개입위치만 살피며 실제파일작성·유무평가는 범위밖입니다. 파일권한 규칙도 내장파일도구에 한정되므로 MCP권한으로 확대해석하지 않습니다. [W18](COURSE_SOURCES.md#w18)의 MCP는 외부add/policy도구이고 금융RAG는 직접Python도구이므로, 3차RAG의MCP노출과 LangGraph클라이언트호출·도메인Skill유무실험은 직접추가해야 합니다.
