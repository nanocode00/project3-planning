# StartFit 팀 개발·리뷰·CI 운영 정책

작성일: **2026-10-28**. 3인 팀의 **합의용 통합 초안**입니다. 1·2차 프로젝트의 공통 운영 규칙과 [CI 사용량 절감 추가안](<GitHub Actions CI 사용량 절감 정책 추가안.md>)을 통합했습니다. 팀 합의와 공식 조 저장소 반영 전이며, GitHub 설정·workflow·검증 도구는 아직 구현하거나 적용하지 않았습니다.

이 문서는 팀 운영 정책의 정본으로 사용합니다. 원본 추가안은 제안 이력으로 보존하며, 향후 운영 규칙은 이 문서에서 갱신합니다. 공식 과제 조건은 [GATES.md](GATES.md)·[EVALUATION.md](EVALUATION.md)·[SCHEDULE.md](SCHEDULE.md)·[DELIVERABLES.md](DELIVERABLES.md)가 소유합니다. CI 절감이나 팀 예외로 공식 조건을 면제하지 않습니다.

## 1. 적용 원칙과 역할

- 팀원과 AI 에이전트 모두 같은 범위·검증·리뷰 규칙을 따릅니다. AI가 작성한 코드·설명·판정도 작성자가 확인하고 책임집니다.
- 한 작업은 하나의 목적을 다룹니다. Spec에 없는 기능, 무관한 정리, 다른 작업의 버그 수정을 함께 끼워 넣지 않습니다.
- 공식 조 저장소의 `AGENTS.md`는 이 정책과 필수 작업 문서의 진입점으로 구성하고 규칙을 중복 복사하지 않습니다. 이 준비 저장소에는 실행용 AGENTS나 workflow를 생성하지 않습니다.
- 담당자는 [TEAM.md](TEAM.md)에서 정합니다. 각 작업에 주담당과 보조/리뷰 담당을 두며, 실명·팀장·저장소 관리자는 합의 전 추정하지 않습니다.
- 공식 일일·주간 점검과 역할 체크리스트는 TEAM.md를 따릅니다. 차단 이슈·다음 작업·결정 책임자를 남기고 실제 회의 기록과 구현 증거를 구분합니다.

## 2. Spec과 문서 책임

기능 구현 전에 목적·성공 기준·범위·동작·계약·완료 조건을 작성합니다. 기능 Spec은 **Why / Goal / What / How / AC**를 포함하고, AC는 정상·경계·실패 시나리오를 검증할 수 있게 씁니다. 제품 코드 구현 전에 SPEC·AGENTS·평가셋 초안을 기록하는 공식 선행 조건도 지킵니다.

| 내용 | 기준 문서의 책임 |
|---|---|
| 제품 범위·우선순위·제외 범위 | 공식 조 저장소 SPEC와 확정 주제서 |
| 기능별 동작·API·데이터·수치·AC | 해당 기능 Spec |
| 공통 구조·인증·상태·도구 경계 | 아키텍처/계약 문서 |
| 공식 조건·숫자·마감·완료 증거 | 이 준비 저장소의 공통 체크리스트를 공식 조 저장소로 이관한 정본 |
| 담당·진척·차단 이슈 | 작업 백로그·팀 운영 기록 |
| 실제 수행·검증·미해결 사항 | Worklog·실험 결과 |

- 하나의 결정·계약·수치는 한 문서가 소유하고 다른 문서는 링크합니다. 기획안 버전을 늘리며 서로 다른 규칙을 정본으로 유지하지 않습니다.
- 실제 동작과 목표 설계를 구분합니다. 중요한 결정의 변경 이유·영향·검토자는 결정 이력에 남깁니다.
- API·DB·상태 계약에는 입출력·오류·권한·파일·환경변수·코퍼스 버전·상태 소유권을 포함합니다. 관련 변경은 같은 PR에서 문서와 구현을 맞춥니다.
- 의미 있는 작업 종료 시 Worklog에 변경 파일·명령·실제 결과·미검증 사항·다음 작업을 남깁니다. 연속 작업은 같은 기록을 갱신할 수 있습니다. 문서/정책 작업은 코드 테스트 대신 링크·정합성 등 적절한 검증을 기록합니다.

## 3. 브랜치·커밋·Issue

- `main` 직접 push를 금지하고 **작업 브랜치 → PR → 리뷰 → 병합** 흐름을 따릅니다.
- 작업 시작 전 status/diff와 최신 원격 main을 확인합니다. 새 작업은 최신 main에서 새 브랜치로 시작하고, 완료한 브랜치를 다른 작업에 재사용하지 않습니다.
- 커밋·PR 제출·병합 전에 main과의 차이와 충돌을 다시 확인합니다. 개인 브랜치는 안전하게 동기화하되 다른 사람이 사용하는 브랜치의 이력을 임의로 재작성하지 않습니다.
- 기존 미커밋 변경을 보존하고 관련 파일만 선별 stage합니다. 작업을 지우는 강제 초기화·일괄 복구·정리 명령을 임의로 사용하지 않습니다.
- 브랜치는 `<type>/<작업명>`, 커밋은 `<type>: <요약>`을 사용합니다. type은 `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `perf`, `experiment`입니다.
- 커밋 요약·PR 제목/본문은 한국어를 기본으로 하고 식별자·명령·고유 기술명은 원문을 허용합니다. 공동 기여자는 기록합니다.
- 재현 가능한 버그는 기존 Issue와 중복을 확인해 환경·입력·기대/실제 동작·증거를 남기고 해결 PR에 연결합니다. 현재 작업과 무관한 문제는 별도 Issue로 둡니다.
- 병합된 작업 브랜치는 후속 PR·다른 팀원의 사용 여부를 확인한 뒤 로컬·원격에서 정리합니다.

## 4. PR 크기·리뷰·병합

- 한 PR은 하나의 논리적 목적을 갖고 변경 이유·결과 동작·영향 범위·검증·미확인 사항을 설명합니다.
- **리뷰 핵심 변경은 400줄 안팎을 권장**합니다. 코드·테스트·설정·Spec·평가기준·실험 절차는 핵심 변경에 포함합니다. lockfile·생성 결과·원시 측정·Worklog는 별도로 구분할 수 있지만 검토를 면제하지 않습니다.
- 400줄을 넘으면 변경 규모·이유·분리하지 않은 이유를 PR에 적고 논리적 커밋으로 나눕니다. 핵심 변경이 매우 크면 책임 단위 PR 분리를 우선 검토합니다. 줄 수만 맞추는 기계적 분할은 하지 않습니다. 2차 저장소의 특정 줄 수 차단 도구를 이번 저장소에 자동 적용한 것으로 보지 않습니다.
- **작성자 외 팀원 최소 1명의 승인**과 필요한 검증 통과 후 작성자가 최종 병합합니다. 자기 승인·AI 의견만으로 팀원 승인을 대체하지 않습니다.
- 수정 요청·미해결 리뷰가 남으면 병합하지 않습니다. 승인 후 코드·설정·판정 기준 등 검토 결론에 영향을 주는 변경이 있으면 재리뷰를 받습니다.
- 병합 직전 최신 head와 base, 충돌, 필수 CI, 승인 유효성, 미해결 코멘트를 확인합니다. 오래된 SHA의 성공 결과로 현재 변경의 검증을 대신하지 않습니다.
- 작성자 부재 등으로 대신 병합하면 사유와 병합자를 기록합니다. 공통 계약·권한·평가·CI 정책 변경은 관련 담당자가 함께 검토합니다.
- 자동 승인·자동 병합은 이 정책에 포함하지 않습니다. 도입하려면 별도 정책 변경으로 주체·권한·검증·예외를 합의합니다.
- main은 실행 가능하고 관련 테스트가 통과하는 상태를 유지합니다. 장애·러너/결제 제한·테스트 미실행을 통과로 보고하지 않습니다.

## 5. 검증·LLM·데이터·평가

- 변경의 AC와 영향에 맞춰 정적 검사·단위·계약·통합·권한/실패 검증을 수행합니다. 구현을 그대로 복사한 테스트나 동일 검사의 중복 실행을 늘리지 않습니다.
- LLM은 의미 해석·근거 기반 제안을 맡고 서버는 인증·소유권·스키마·인용 ID·날짜/금액 계산·승인 버전·중복 저장을 검증합니다. LLM 출력으로 권한을 확정하지 않습니다.
- 프로필·DB Store의 시멘틱 메모리·실행 체크포인트·준비 상태는 역할을 구분하고 사용자별 접근을 검증합니다. 기억 검색·정정·삭제와 승인 버전 변경 시 재검토는 관련 Spec과 회귀 검증에 반영합니다.
- `.env`, 비밀번호, 토큰, 키, 실제 개인 상담 원문을 Git·공개 Issue·테스트 fixture·로그·artifact에 넣지 않습니다. `.env.example`은 비밀값 없이 제공하고 관측 입력은 최소화·마스킹합니다.
- 공개 코퍼스도 접근·이용·재배포 조건을 확인합니다. 모델 가중치·대용량 데이터는 Git/일반 PR artifact에 넣지 않고 버전·출처·해시·재현 경로를 남깁니다.
- 질문 작성·정답 근거 판정을 교차 배정하고 평가 정답·라벨이 운영 모델 입력에 섞이지 않게 합니다. 동결 원본·제외 기록·동일 v2 비교 규칙은 GATES.md를 따릅니다.
- 평가 문항·판정·코퍼스·모델·프롬프트 변경은 영향과 비교 조건을 기록하고 리뷰합니다. 결과가 유리해지도록 원시 응답·불리한 문항을 바꾸거나 숨기지 않습니다.
- 개발용 fixture/재생, 로컬 실제 실행, 라이브 provider 평가, 배포 검증은 구분합니다. 재생 PASS를 실제 모델 품질이나 최신 데이터 확인의 증거로 쓰지 않습니다.
- 무거운 실험은 사전 목적·비교 조건·예산·실행 환경·명령·기대·중단 조건을 남깁니다. 실제 결과에는 코드/평가셋/코퍼스 버전과 비용·시간·실패를 기록합니다. 공식 한도는 EVALUATION.md를 따릅니다.

## 6. CI 변경 범위와 필수 결과

CI 절감 순서는 **영향 범위 선택 → 중복 실행 제거 → 캐시/설치 최소화 → 무거운 검증 분리 → artifact/matrix 축소**입니다. 필요한 테스트를 삭제하거나 검증 실패를 무시해 사용량을 낮추지 않습니다.

### 6.1 변경 분류

실제 폴더 구조가 확정되면 분류 규칙에 정확한 경로를 기록합니다. 아래는 영역 기준이며 `backend/`·`frontend/` 폴더가 이미 있다는 뜻은 아닙니다.

| 변경 영역 | 실행할 검증 |
|---|---|
| API·검색·그래프·저장·사용자 기억 | 관련 백엔드 단위/계약/통합·평가 회귀 |
| UI만 변경 | 프런트 lint·타입·테스트·필요한 build smoke |
| 공통 API/schema·인증·환경·DB migration·compose | 영향받는 양쪽과 공통 통합/기동 검증 |
| 프롬프트·Skill·판단 규칙·도구 정의·평가셋/판정·코퍼스 manifest | 관련 서버/계약·평가 회귀·동결 해시 검증 |
| workflow·CI 분류기·의존성/lock·Docker 설정 | 영향받는 job·workflow/분류 규칙 검증·비용 검토 |
| 순수 설명 문서·LICENSE·Issue 양식만 변경 | 저비용 문서/정책·secret scan·필수 집계. 무관한 제품 job 생략 |
| 알 수 없는 경로·불완전한 diff·분류 오류 | 제품 검증 전체 실행으로 전환. 파일 목록 자체를 확보 못 하면 집계는 실패 처리 |

- **확장자나 `docs/**`만으로 docs-only를 판정하지 않습니다.** `AGENTS.md`, 실행에 읽히는 Markdown/Skill, 핵심 Spec·계약·평가 규칙의 변경은 관련 검증 대상입니다. 정책 변경은 정책·CI 영향도 별도 검토합니다.
- PR diff는 base/head의 merge-base 기준으로 계산하고 삭제·이름 변경의 이전/새 경로도 판정합니다. main push는 before/after 차이를 사용합니다. 파일 누락이나 Git 오류를 빈 변경으로 처리하지 않습니다.
- 문서와 코드가 섞이면 필요한 job의 합집합을 실행합니다. 각 job의 실행/생략 이유를 결과에 남깁니다.

### 6.2 required check의 일관성

- 모든 PR에서 변경 판정과 필수 결과 집계를 실행하고, 분류에 따라 제품 job만 조건부 실행합니다. 필수 workflow 전체를 `paths`로 생략해 결과가 영원히 대기하는 구조를 피합니다. GitHub의 [경로 필터·skip 동작](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#onpushpull_requestpull_request_targetpathspaths-ignore)을 기준으로 구현합니다.
- 필수 집계 check 이름은 **`ci-required`를 제안**하며 공식 저장소에서 확정합니다. 항상 집계를 시도하도록 구성하되 취소·미실행 자체를 성공으로 바꾸지 않습니다.
- 집계는 변경 판정 성공, 저비용 정책/secret 검사 성공, **실행 대상 job 전부 성공**일 때만 성공합니다. 판정 오류·실패·취소·결과 누락·예상 밖 skip은 실패입니다. docs-only처럼 분류 결과상 불필요한 job의 skip만 허용합니다.
- `continue-on-error`, 무조건 성공 처리, 과거 실행의 녹색 check로 필수 실패를 덮지 않습니다. 실제 job 결과와 실행 SHA를 집계 근거로 사용합니다.
- 보호 브랜치에 승인·필수 check를 설정할 때 docs-only와 혼합 PR을 실제 확인합니다. 문서 작성은 branch protection 설정 완료를 뜻하지 않습니다.
- 정책 검사와 secret scan은 순수 문서 PR에서도 유지합니다. workflow 토큰 권한은 최소화하고, 외부 PR 코드를 secret/쓰기 권한이 있는 `pull_request_target` 문맥에서 실행하지 않습니다.

## 7. CI 실행·의존성·비용 절감

| 항목 | 운영 규칙 |
|---|---|
| 트리거 | 일반 PR은 `pull_request`, push 검증은 필요한 main 등으로 한정. feature push+PR에서 같은 검사를 중복 실행하지 않음. 병합 후 main 통합 확인·배포처럼 목적이 다르면 유지 가능하며 이유 기록 |
| 중복 취소 | 일반 PR 검증은 workflow+PR 번호를 포함한 고유 concurrency 그룹과 `cancel-in-progress: true` 사용. 다른 PR·workflow는 취소하지 않음. SHA를 키에 넣으면 이전 SHA 취소가 안 되므로 결과 보존 목적의 예외에서만 사용 |
| 부수효과 | 배포·migration·외부 저장처럼 취소 시 중간 상태가 생기는 job은 검증 취소 그룹과 분리하고 직렬 실행·중단/복구 방식을 별도 정의 |
| Timeout | 모든 runner job에 `timeout-minutes` 명시. 네트워크·설치·polling·외부 호출에도 유한 대기 설정. 정책5분·단위검증15분 등은 초기 예시이며 실제 측정 후 조정 |
| 설치 | job에 필요한 의존성만 설치. 일반 PR에 GPU/CUDA·학습 환경·대형 모델을 일괄 설치하지 않음. 실제 DB·클라이언트가 필요한 계약/통합 테스트 의존성까지 임의로 제거하지 않음 |
| 캐시 | package manager 다운로드 캐시 우선 사용. OS·런타임·requirements/lock 변경이 키에 반영되도록 구성. 복원 시간·적중률을 측정하고 효과 없으면 조정. 비밀값·사용자 데이터는 캐시하지 않음 |
| Rerun | runner/registry/provider의 명확한 일시 장애 등 원인을 확인한 제한된 재실행만 허용. 같은 원인 재발 시 중단·수정 후 실행. flaky 재시도도 원래 실패와 원인 기록을 남김 |
| Artifact | 후속 검토에 필요한 결과만 보존. 일반 PR은 짧은 기간(예: 3일)을 사용하되 필수 제출 증거·원시 결과·동결 manifest는 별도 지속 보관. checkpoint·학습 데이터·node_modules·가상환경·전체 캐시는 일반 artifact로 올리지 않음 |
| Matrix | 일반 PR은 배포 기준의 대표 환경 1개를 기본으로 검증. 필요한 호환성 matrix는 수동/정기/release로 분리하고 지원 범위에 맞춰 실행 |
| 실측 | 변경 전후 실행 job 수·시간·대기/취소·캐시·artifact 사용량을 기록. 병렬화로 벽시계 시간만 줄어든 것을 사용량 절감으로 단정하지 않음 |

concurrency의 취소·그룹 동작은 [GitHub 공식 문서](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency), trigger·timeout·캐시는 [workflow 문법](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax)을 확인해 구현합니다. 추가안의 action 버전·경로·시간은 예시이며 복사만으로 적용 완료로 보지 않습니다.

## 8. 일반 PR 검증과 무거운 검증

| 구분 | 포함할 검증 | 실행·증거 |
|---|---|---|
| 일반 PR | lint·타입·단위·schema/contract·가벼운 통합·필요한 build smoke·정책·secret 검사, 관련 평가 회귀·동결 해시 | 변경 범위별 CI 실행 결과와 SHA |
| 무거운 검증 | 실제 provider·GPU·대형 모델·전체 평가/benchmark·전체 E2E·긴 Docker build·호환성 matrix | 수동 workflow·필요한 정기 실행·전용 runner·재현 가능한 로컬 실행·release 검증 중 적합한 방식, 결과와 명령 기록 |

- **과제의 평가 회귀·동결 해시 확인을 CI에서 빼지 않습니다.** 일반 PR에는 작은 fixture/기록 응답을 이용한 회귀·판정/해시 검증을 두고, 실제 provider 결과와 구분합니다.
- 외부 유료 호출·전체 v2 실험을 매 PR에 반복하지 않더라도, 관련 변경 뒤와 최종 제출 코드에서 실제 품질·비용·시간을 재측정해 공식 증거를 남깁니다. 과거 실측이 현재 변경에 유효한지 확인합니다.
- 무거운 검증을 분리할 때 실행 책임자·유발 변경·수행 시점·결과 보관·배포/완료 전 통과 여부를 정합니다. 수동 실행은 선택적 생략을 뜻하지 않습니다.
- 절감 목적의 정기 실행도 변경·필요성이 없는 반복을 줄입니다. 실패한 무거운 검증을 로컬 fixture 성공으로 대체하지 않습니다.

## 9. 변경 승인·예외·적용 확인

- 이 정책·workflow·의존성·필수 check·평가 기준을 바꾸는 PR에는 영향·비용·필요한 검증·권한 변경을 설명하고 다른 팀원의 리뷰를 받습니다.
- 예외가 필요하면 사유·대상 PR/SHA·대체 검증·검토자·유효 범위를 기록합니다. 한 번의 러너/비용 장애 예외를 상시 CI 우회로 일반화하지 않습니다. 공식 제출 요건은 별도로 충족합니다.
- CI 완료 보고는 정적 문법/분류 테스트, 실제 Actions 실행, 관리자 설정, 라이브 품질 평가를 구분합니다. 러너가 시작되지 않은 결제 제한은 코드 실패도 통과도 아닙니다.

### 공식 저장소 적용 체크리스트

- [ ] 팀이 이 정책을 검토하고 담당·리뷰/병합 책임을 확정했다.
- [ ] 확정 폴더 구조로 변경 범위와 공통 영향 파일을 매핑했다.
- [ ] 순수 문서·서버·UI·혼합·Skill/평가·삭제/이름 변경·미분류/오류에서 선택 검증이 맞는지 확인했다.
- [ ] `ci-required` 등 합의된 필수 집계의 성공·실패·취소·예상 밖 skip·판정 오류 처리를 확인했다.
- [ ] 실제 PR에서 중복 trigger·concurrency·timeout·설치/캐시·artifact/matrix 비용을 확인했다.
- [ ] 보호 브랜치·팀원 승인·필수 check 설정과 병합 가능 여부를 실제 확인했다.
- [ ] 무거운 검증의 책임자·시점·명령·예산·증거 보관 위치를 정했다.
- [ ] 일반 PR 평가 회귀/동결 해시와 최종 실제 평가 증거를 구분해 연결했다.
- [ ] 완료 체크는 실제 결과 경로·SHA·확인일이 있을 때만 표시했다.
